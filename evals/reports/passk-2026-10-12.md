# pass^k, haiku and sonnet, k = 3, 2026-10-12

**Status: first repeat-run measurement. One agent, one corpus, three runs each.** Nothing
here feeds the gate. Reports: [`repeats-2026-10-12/`](repeats-2026-10-12/).

## Why

Every number in this repo so far is one run per task. A task that passes once and fails the
next time is a flaky test with good PR, and a single-run pass rate cannot show it. So the
same unchanged agent (`research-agent` `v1`, 40 tasks) was run three times per model, and
this reports, per layer, the share of tasks that passed **all three** times (pass^3), the
share that passed **at least once** (pass@3), and the tasks that flip.

## Method

- `python -m evals.runners.claude_code --model haiku|sonnet`, three times each, one after
  another, concurrency 4 inside a run. The agent, prompt, corpus and context files are the
  same for all six runs.
- Raw transcripts kept (`evals/keep_runs.py`), so the trace checks here use the tools'
  real output, not a replay.
- Stored answers pseudonymised the same way as the baseline (see the README); scores were
  computed before that and are unchanged.
- Grouping is by alias **and the model the alias resolved to**. `evals.passk` refuses to
  pool runs when one alias resolved to different models.

## These are not the baseline's models

The 23 Sep baseline ran `claude-haiku-4-5`, `claude-sonnet-5` and `claude-opus-5-5`, on
Claude Code 2.1.280. On 12 Oct the same `--model haiku` and `--model sonnet` resolved to
`claude-haiku-5-5` and `claude-sonnet-5-5`, on Claude Code 2.1.294. The alias is not a
version. So the baseline is **not** run 1 of anything here, and the drop in outcome rate
between the two (haiku 52% to 19%, sonnet 40% to 12%, same layer, uncorrected) is a model
change plus a reconstructed context file set, not a regression of the agent. Opus was not
re-run.

The gate keyed its series on the alias alone, so this change would have read as a
regression. It now keys on the resolved model too (`evals/gate.py`, with tests): a report
from a new model starts a new series with no baseline, and is not compared.

## What it shows

- **The aggregate holds still while the tasks do not.** Single-run rates barely move
  between identical runs: haiku outcome 18-20%, grounding 57-68%. Underneath, 10 of 40
  tasks change outcome verdict at least once, and 15 of 40 change grounding verdict. The
  grounding rate falls from 62% (single run) to 40% (pass^3) for haiku, and from 78% to
  60% for sonnet. Tool choice falls from 42% to 25% for haiku.
- **Almost nothing passes every layer, every time.** pass^3 on `all_layers` is 0/40 for
  both models, and outcome pass^3 is 3/40 for both. The outcome layer still carries the
  regex flaw (a debunking that repeats a bad figure is failed), so its level says little
  about accuracy. The gap between pass@3 and pass^3 does say something: 13 versus 3 for
  haiku.
- **The gate's tolerance is above the noise, on this evidence.** The largest gap between
  two runs of the same unchanged agent on a gated layer is 7 points (sonnet, outcome);
  the gate fails at 15. Three runs give a lower bound on the spread, not the spread.
- **Flips by category are too few to read.** Haiku: tech-comparison 3 of 6, fact-check 3
  of 7, lead 0 of 6. Counts that small are consistent with no clustering at all.

The gate fails a PR that loses more than 15 points on `all_layers` or `outcome`. The largest gap between two runs of the same unchanged agent here is 7 points (sonnet, outcome), below the tolerance.

## Limits

- k = 3, one agent, one fixture corpus, two models. pass^3 intervals are wide.
- The context files the runs read are a reconstruction (see
  `trace-scores-2026-10-12.md`), not the ones the baseline read.
- The trace rows were scored with the current scorer, which is still uncalibrated; the
  30-trace hand-label set (`evals/judges/trace_labels.py`) is the next step for that.
- Opus was not repeated: slowest and heaviest on quota, and the result does not depend on it.
