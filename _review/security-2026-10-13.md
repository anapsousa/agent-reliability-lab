## MEDIUM

### MEDIUM-1. Judge `claude -p` calls rely on a stale tool blocklist and still inherit user settings, while reading untrusted third-party text
- evals/judges/run_llm_judge.py:28-62 (`JUDGE_DISALLOWED_TOOLS`, `judge_argv`), called from run_llm_judge.py:92-99 and evals/judges/stance.py:87-94.
- The argv disables 14 built-ins by name and passes `--tools ""` and `--strict-mcp-config`, but it does not pass `--setting-sources ""` (the agent runner does, claude_code.py:100-101) and it never checks which tools the CLI actually offered (the runner does, claude_code.py:339-344). The blocklist is a name list; any tool the CLI adds or that is not on the list stays available under whatever permissions Ana's user settings grant. This session's own tool list includes built-ins that are not in the list (for example Monitor, EnterWorktree, ExitWorktree, SendMessage, TaskStop). Whether the installed CLI would run one of them without a prompt under her allow-list was not tested.
- Exploitability: the judged text includes answers quoting third-party web pages (real-vendor set, run_llm_judge.py:15-22) and agent answers produced from untrusted fixtures; a passage can say "ignore the rubric, do X". The code comment itself records that a bare `claude -p` obeyed such a prompt in another project. Today the inputs are curated, so this is MEDIUM, and it rises to HIGH if raw agent output is judged automatically (the comment says the same).
- Fix: add `--setting-sources ""` and `--no-session-persistence` to `judge_argv`; switch to `--output-format stream-json --verbose` and assert the init event's tool list is empty, as claude_code.py:339-344 does; keep the name blocklist only as a second layer. Run the judge with `cwd` set to a fresh temp dir so no CLAUDE.md or project settings load. Add a test that fails when the init tool list is non-empty.

### MEDIUM-2. Public repo with no automated backstop against committing the private context
- Repo settings above: secret scanning off, push protection off, `main` unprotected. `.gitignore:15` (`agent/*/context/*`) is the only barrier keeping `agent/*/context/*.md` (real business context, present on disk next to the committed `*.example.md` files) and `evals/runs/` out of the repo. History is currently clean (table above), but one `git add -f`, a changed ignore rule, or a new output path (`trace_rescore --out`, `rescore --json`, `keep_runs --dest`) would publish it, and the redaction in the runner is email-only (LOW-3). The 2026-09-15 review already noted the repo "is meant to go public"; it is now public.
- Fix: enable secret scanning and push protection in repo settings; protect `main` (require the `Tests and lint` job and PR review); add a CI step and a pre-commit hook that fail if `git ls-files 'agent/*/context/*' | grep -v -e '\.example\.md$' -e README.md` is non-empty or if any tracked file contains `/Users/`; add a CODEOWNERS or required review for `.gitignore` and `.github/`.

## LOW

### LOW-1. Workflow has no `permissions:` block and uses mutable-tag third-party actions (carry-over from the 2026-09-15 review)
- .github/workflows/eval-gate.yml:13, 34, 58 (`actions/checkout@v4`) and :16, 37, 63 (`astral-sh/setup-uv@v3`); no `permissions:` key anywhere. The earlier review said to add `permissions: contents: read` and pin actions to commit SHAs before the repo went public; neither was done.
- Exploitability: mitigated today, because the repo default workflow permission is `read`, the trigger is `pull_request` (not `pull_request_target`), and the jobs use no secrets. A compromised or retagged `setup-uv@v3` would run code on the runner with a read-only token and could tamper with that run's result only. Hardening, not an active hole. If the repo default is ever changed to read/write, the same compromise would be able to push.
- Fix: add `permissions: contents: read` at the top; pin both actions to full commit SHAs with a version comment; enable Dependabot for `github-actions`.

### LOW-2. Expression interpolated into a shell `run:` and a self-attesting gate
- .github/workflows/eval-gate.yml:75 runs `uv run python -m evals.gate --base origin/${{ github.base_ref }}`. `base_ref` is the target branch name, which a fork PR author cannot choose (it must exist in the base repo), so it is not exploitable by outsiders; it is still the unsafe pattern (a collaborator who can create a branch named with shell metacharacters would get command execution in the job).
- Related design note: the gate (evals/gate.py:101-115) executes from the PR's own checkout and compares report files that the same PR supplies, so a PR can edit gate.py or the reports to pass. It is a policy check for the owner's own PRs, not a security boundary. gate.py:40-43 and :106-107 pass arguments as lists with no shell, which is correct.
- Fix: pass `${{ github.base_ref }}` through `env:` and use `"origin/$BASE_REF"`; run the gate from the base branch's copy (checkout base to a second path) if it is ever meant to bind external contributors.

### LOW-3. Redaction before publishing is email-only
- evals/runners/claude_code.py:56-61 (`redact` replaces only email-shaped strings), applied to `answer` (:359) and `stderr_tail` (:351). Reports are written straight into the tracked `evals/reports/` directory (:442-444). Paths such as `/Users/<name>/...`, tokens, or text copied from the private context files would pass through unredacted if the agent or the CLI emitted them. Scan found none today (table above).
- Fix: extend `redact` to home-directory paths (`/Users/`, `/home/`), common key patterns, and the user name; add a test that runs the scanner used in MEDIUM-2 over `evals/reports/*.json` and fails the build on a hit.

### LOW-4. Locally generated markdown reports may embed private-context-derived output
- evals/trace_rescore.py:50-52 and :194-203 replay `read_context` from the private files when they are present, and `--out` writes the result (:272-273). The committed evals/reports/trace-scores-2026-10-12.md was produced with context present (its header says so, line 62). I found no private-only figure or phrase in it. The pipeline has no check that stops one from landing there.
- Fix: covered by the scanner in MEDIUM-2; additionally make `trace_rescore` refuse `--out` inside the repo when `context_available()` is true unless `--allow-private` is given.
